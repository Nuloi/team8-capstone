# 혼잡 판단 알고리즘 설계

작성: 2026-10-06 (팀 합의 — 변경 시 사용자 확인).
**목표: "그 시간대 버스가 얼마나 혼잡한가"와 "언제 시간대가 비는가"를 노선·방향·정류장별로 판단해 웹 파트에 파일로 넘긴다.**
재차율 자체를 예측하는 것이 목표가 아니다(팀 결정 2026-10-06). 결과의 중심은 **혼잡 등급과 시간대**다.
입력: `data/clean/51130/*.csv` (미래캠퍼스 노선만, 2025년), 공휴일·학사일정 설정.

## 0. 데이터 제약 → 설계 원칙
| 제약 | 원칙 |
|---|---|
| 시간 해상도 1시간(`tzon`) | 결과는 "몇 시대"까지만 말한다 |
| 합성데이터, 한 운행 안에서도 값 변동 큼 | 개별 관측이 아니라 **날별 평균의 분포**로 판단 |
| 2025년 1년치뿐 | 연도 계절성은 다루지 않는다. 대신 **학기/시험/방학/계절학기** 차이를 쓴다 |
| 칸마다 관측일 수가 다름 (새벽·외곽은 적음) | 관측이 적은 칸은 상위 평균 쪽으로 **보정(shrinkage)** |
| 혼잡을 판단할 값은 `cgst`(45명 기준 재차율 **추정**) 하나뿐 | 내부에서 등급을 매기는 데만 쓰고, 결과는 등급·시간대 중심으로 낸다 |
| 방향 정보 없음 | 노선 내 정류장 순서로 **상행/하행**을 추정한다 (아래 1.1) |

## 1. 분석 단위 ("칸")
| 단위 | 칸 | 답하는 질문 |
|---|---|---|
| **버스** | 기본번호 × **방향** × 기간 × 일자유형 × 시간대 | "34번 상행 버스, 학기 평일 8시에 얼마나 혼잡한가" |
| **정류장** | 기본번호 × 정류장 × 기간 × 일자유형 × 시간대 | "34번, 원주의료원(상행)에서 8시에 얼마나 혼잡한가" |
| 변형(세부) | 변형 rte_id × 정류장 순서 × … | 변형 노선별 세부 |

- 칸 안에서 **날짜마다 평균 cgst를 하나** 만든다 → "날별 값" `x_1 … x_d` (d = 관측일 수). 버스 단위는 그 방향의 모든 정류장 관측을 합친 평균.
- 이후 모든 지표는 날별 값 기준이다.

### 1.1 상행/하행 판정 (팀 결정: 같은 이름 정류장은 상행·하행으로 구분)
원주 노선은 대부분 왕복형(기점 → 회차 → 기점)이라 같은 이름의 정류장이 갈 때·올 때 한 번씩 나온다.
1. 노선(rte_id)마다 **이름이 같은 정류장 쌍의 중간 순서**들을 구하고, 그 **중앙값을 회차 지점**으로 본다 (예: 34-1번은 쌍 43개의 중간점이 대부분 71.5~72번째).
2. 회차 지점 **이하 = 상행**(기점 → 회차), **이후 = 하행**(회차 → 기점). 쌍이 없는 노선은 순서 범위의 가운데를 회차 지점으로 쓴다.
3. 기본번호 단위에서 한 정류장의 방향이 변형마다 다르면 **관측이 많은 쪽**을 따른다.
4. 표시명 `sttn_label` = `정류장명(방향)`. 상행·하행으로도 같은 이름이 남으면(회차 지점 근처·갈래 노선) 정류장 ID 뒤 4자리를 붙인다: `구억동(상행·0241)`.

## 2. 지표와 등급
| 지표 | 정의 | 의미 |
|---|---|---|
| 수준 `L` | 보정 평균 `(d·mean(x) + k·prior) / (d + k)` — `prior` = 같은 노선(버스: 같은 노선·방향·기간·일자유형의 전 시간대, 정류장: 같은 노선·기간·일자유형·시간대의 전 정류장) 평균, `k` = 5 | 보통 얼마나 붐비나 |
| 상위값 `P90` | 날별 값의 90분위 | 붐비는 날엔 얼마나 |
| 빈도 `F` | `x_i ≥ T_혼잡`인 날의 비율 | 얼마나 자주 |
| 시간 지속 `D_t` | 같은 날·칸에서 `T_혼잡` 이상이 연속된 시간 수의 평균 | 얼마나 오래 |
| 구간 지속 `D_s` | 같은 날·시간대에 노선 순서상 연속으로 `T_혼잡` 이상인 정류장 수의 평균 (변형 단위) | 어디까지 이어지나 |

**혼잡 등급 3단계 (임시 기준, 팀 결정 2026-10-06)** — `T1` 여유 / `T2` 보통 / `T3` 혼잡
- 경계: 수준 `L` 분포의 **하위 1/3(33분위)·상위 1/3(67분위)**. **버스 단위와 정류장 단위 경계를 따로** 계산한다(변형 단위는 정류장 경계 사용).
- 경계값은 실행할 때마다 그때까지의 데이터로 다시 계산하고 `grade_thresholds.csv`에 기록한다(웹 범례용).
- **임시 기준**이다 — 2025년 수집이 끝나면 다시 결정한다(아래 6장의 문제점 참고). 등급 방식은 설정값으로 둔다.
- `T_혼잡`(빈도·지속 계산 기준) = 각 단위의 `T3` 경계.

## 3. 결과물 — "얼마나 혼잡한가"와 "언제 비는가"
| 질문 | 결과 |
|---|---|
| 그 시간대 **버스**가 얼마나 혼잡한가 | `bus_hourly.csv` — 노선·방향·기간·일자유형·시간대별 등급, 그 시간 가장 붐비는 정류장 |
| 그 시간대 **정류장**에서 얼마나 혼잡한가 | `pattern_base.csv` (세부: `pattern_route.csv`) |
| 언제 **혼잡**하고 언제 **비는가** | `time_windows.csv` — 버스·정류장 단위로 **혼잡(T3) 연속 구간 + 피크**, **여유(T1) 연속 구간 + 가장 한산한 시간** |
| 혼잡할 때 **언제 타면 덜 붐비나** | `recommendations.csv` — T3 칸마다 **같은 날 안에서 가장 가까운 여유(T1) 시간**, 여유가 없으면 가장 가까운 보통(T2) 시간 (거리 같으면 `L` 낮은 쪽). 범위 제한은 설정 `recommend_max_shift_hours`(0 = 제한 없음) |

예: "학기 평일 34번 상행: 08~18시 혼잡(피크 15시), 06시·22시 여유" / "34번 상행 9시 혼잡 → 6시(여유) 추천"

## 4. 웹 파트에 넘길 결과물
**역할 경계**: 이 저장소는 알고리즘까지 구현하고 결과를 **파일로 넘긴다.** 웹 화면 구현은 다른 팀원 담당이다.
결과 파일의 컬럼·형식은 웹 팀원과의 계약이므로 확정 전에 함께 맞춘다(형식: CSV `utf-8-sig`, 필요하면 JSON 추가 — 미정).

실행: `python -m bus_congestion pattern --year 2025` (먼저 `clean`) → `data/result/51130/2025/`
코드: `src/bus_congestion/pattern.py`, `matching.py`(방향·표시명), 설정: `config/settings.toml [pattern]`

| 파일 | 한 행 | 주요 컬럼 |
|---|---|---|
| `bus_hourly.csv` | 기본번호 × 방향 × 기간 × 일자유형 × 시간대 | `grade`, `grade_name`, `level`, `est_pax`, `n_days`, `congested_days_ratio`, `duration_hours`, `peak_sttn_label`(그 시간 가장 붐비는 정류장) |
| `pattern_base.csv` | 기본번호 × 정류장 × 기간 × 일자유형 × 시간대 | `sttn_label`, `direction`, `grade`, `grade_name`, `level`, `est_pax`, `n_days`, `n_obs`, `cgst_mean_raw`, `cgst_p90`, `congested_days_ratio`, `duration_hours` |
| `pattern_route.csv` | 변형 × 정류장 순서 × … | 위 + `rte_id`, `rte_no`, `sttn_seq`, `segment_stops` (`direction`은 그 변형 기준, `sttn_label`은 정류장 단위 기준) |
| `time_windows.csv` | 연속 구간 하나 | `scope`(버스/정류장), `kind`(혼잡/여유), `start_tzon`·`end_tzon`(포함, 10~13 = 10:00~13:59), `hours`, 혼잡이면 `peak_tzon`·`peak_level`, 여유면 `calmest_tzon`·`calmest_level` |
| `recommendations.csv` | T3 칸 하나 | `scope`, `from_tzon`, `rec_tzon`, `rec_grade`·`rec_grade_name`, `shift_hours`(음수 = 더 일찍) |
| `grade_thresholds.csv` | 단위당 1행 (버스, 정류장) | `t_low`, `t_high`, 데이터 기간, `provisional=True` |

- `duration_hours`: 그 시간대가 혼잡했던 날들에 대해, 혼잡이 이어진 시간 수의 평균 (혼잡한 날이 없으면 빈칸)
- `segment_stops`: 그 정류장이 혼잡했던 날·시간에 대해, 노선 순서상(관측된 정류장 기준) 연속 혼잡 정류장 수의 평균
- 숫자 컬럼(`level`, `est_pax` 등)은 근거 확인용이다. 웹 표시는 `grade_name`과 시간대 중심으로 한다.

## 6. 실행 결과로 본 점 (2025-01-01~05-31, 151일)
- 임시 경계: 버스 T1 < 8.91 ≤ T2 < 12.17 ≤ T3 / 정류장 T1 < 9.03 ≤ T2 < 13.19 ≤ T3 (재차율 %)
- 기간 효과 확인: 평균 L 학기 12.5 / 시험 13.75 / 계절학기 10.9 / 방학 10.6. 연세대 정류장 평일은 학기 11.6 vs 방학 7.4
- 상행/하행: 같은 이름 정류장 90개 모두 표시명으로 구분됨 (21개는 ID 뒤 4자리로 추가 구분)
- 추천: 버스 단위 T3 칸 549개 중 515개, 정류장 단위 21,566개 중 21,202개(98%)가 추천을 받음. 추천이 없는 칸은 같은 날 다른 모든 시간도 T3인 경우
- **문제점 — 전체 1/3 분위수 기준의 한계**: 경계를 모든 기간·일자유형을 합친 분포로 정하기 때문에, 붐비는 맥락(학기 평일)은 하루 대부분이 "혼잡"이 된다. 예) 34번 상행 학기 평일 08~18시 전부 혼잡, 여유는 06·22시뿐 → "언제 비는가"가 잘 드러나지 않는다. 최종 기준 결정 시 **맥락 안에서의 상대 등급**(같은 노선·방향·기간·일자유형의 시간대끼리 비교)을 대안으로 검토한다.
- 칸당 관측일 수 중앙값 3일 (25%가 1일) → 보정의 영향이 크다. 1년치가 모이면 완화
- 노선 목록에 없는 rte_id가 생기면 기본번호가 비므로, 수집 기간에 맞춰 `reference` 스냅샷을 추가해야 한다

## 7. 결정 기록
- 2026-10-06: 2단계 "재차율 예측 모델"(그래디언트 부스팅)은 **진행하지 않는다** — 목표는 혼잡 정도와 빈 시간대이며, 1단계를 확장해 버스 단위 등급·여유 구간·추천 개선·상행/하행 구분을 구현했다.
- 남은 결정: 등급 최종 기준(전체 분위수 / 맥락 내 상대 등급 / 고정값), 상습 혼잡 기준, 결과 파일 형식(웹 팀원과 합의)
